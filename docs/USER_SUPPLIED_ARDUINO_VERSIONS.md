# Arduino 개발 스케치 7종 — 사용자 제공 원문 6종과 후속 제안 1종

> `01`~`06`은 사용자가 과거·현재 대화에서 제공한 코드 텍스트를 그대로 보존한 자료입니다. `07`은 이번 대화에서 **ChatGPT가 06번을 참고해 제안한 수정 코드**이며 사용자가 실제 Arduino 보드에 업로드했다고 확인된 코드가 아닙니다. 각 스케치의 정확한 제작일, 실제 업로드 여부, 최종 채택 여부는 별도로 확인되지 않았습니다. 파일 번호가 실제 개발 날짜를 입증하지는 않습니다.

## 확보된 코드별 특징

| 파일 | 관찰된 구현 | 코드 자체의 한계 |
|---|---|---|
| `01_color_and_human_stop.ino` | TCS34725, 1초마다 RGB 읽기, 버튼 기동, `r>=5 || receivedNumber>=1`이면 정지, IR 추종 | 1초 색상 검사도 **시리얼 입력이 있을 때만** 실행; 센서값만으로도 정지; 최초 버튼 이후 지연 루프 |
| `02_serial_echo_test.ino` | Python의 한 줄을 받아 echo하는 시리얼 실험 | 실제 정지·IR·색 센서 기능 없음 |
| `03_rgb_button_result_experiment.ino` | `ColorValues:r,g,b`, `ButtonState:`를 보내며 결과 `0/1`에 따라 정지/라인 추종 의도 | `TCS.getRawData(&red,...)`에 `int*`를 전달(라이브러리의 `uint16_t*` 매개변수와 불일치); `Serial.read()`는 텍스트 문자 `'0'`/`'1'`를 48/49로 반환하므로 결과 비교 실패 가능. 버튼은 INPUT_PULLUP의 LOW가 누름인데 raw 값을 보냄 |
| `04_motion_state_first_attempt.ino` | 300ms 간격 수신 시도, 버튼으로 `moving=1`, 수신값이 0이 아니면 `moving=0` | **`moving=0`만으로 모터 PWM을 0으로 설정하지 않음**. 실제 물리 정지를 보장하지 않음 |
| `05_motion_state_300ms.ino` | `moving` 부울 상태, 버튼 후 300ms 주행, `receivedNumber!=0`이면 `stop()` | 300ms 버튼 루프가 응답 처리보다 먼저 실행될 수 있음. 초기 `receivedNumber=0`은 Pi에서 명시적으로 받은 0인지 구분 불가 |
| `06_stop_on_300ms_communication.ino` | 300ms 검사마다 `stop()`을 추가한 후, 100ms 경과 시 주행 재시도를 의도한 듯한 코드 | `lastCommunicationTime=currentTime` 직후 `currentTime-lastCommunicationTime>=100` 검사는 **항상 거짓**. 동일 루프 후반의 `moving` 조건이 다시 `move()`할 수 있어 통신 시 안전 정지 보장 안 됨 |
| `07_motion_state_after_serial_poll.ino` *(후속 제안)* | 300ms 간격의 수신 확인 뒤 `moving && receivedNumber==0`이면 `move()`; 수신값이 0이 아니면 루프 말미에 `stop()` | **06의 불가능한 100ms 분기는 제거**. 버튼 입력 시 300ms 동안 강제 `move()`하는 블로킹 루프, 수신값이 0이 아니어도 버튼/기존 `moving` 조건에서 루프 말미까지 일시 주행 명령 가능. 최종 버전·실장 성공 여부 미확정 |

모든 스케치 중 라인트레이서 기능을 포함하는 주요 버전에서 확인되는 공통 핀:
`LmotorCW=5, LmotorCCW=6, RmotorCW=9, RmotorCCW=10, IRL=7, IRR=8, BUTTON_PIN=3`. 보드레이트 `9600`, 모터 `speed=255`도 여러 버전에서 확인됩니다. **이 수치가 전체 과제의 최종 확정 배선 및 성능 설정이라는 별도 검증은 아닙니다.**

## Python 시리얼 테스트 코드도 별도 보존

제출된 `historical_snippets/02_serial_echo_test.py`는 Python `pyserial`로 `/dev/ttyACM0` 포트에 `9600bps`로 접속하고 Arduino로부터 한 줄을 읽은 뒤, `Hello from Raspberry Pi!`를 쓰는 **기초 송수신 시험 코드**입니다. 같은 폴더의 `02_serial_echo_test.ino`와 개발 의도가 대응하지만, 정확히 같은 시점·장치에서 동시에 시험됐는지는 사진만으로 확정되지 않습니다. 이 코드는 **최종 라인트레이서 사람 감지 제어 코드가 아닙니다.**

## 사용자 직접 확인: 최종 역할은 확정, 개발 버전별 전송 형식은 별도

**실제 완성 시스템에서는 Pi가 사람 수를 0/1 존재 신호로 바꾸어 보내고 Arduino가 색상 정지구간을 판정했습니다.** 아래 스케치는 중간 개발 단계이며 `people_num` 직접 전송이나 Pi의 RGB 판단을 최종 구현으로 취급하면 안 됩니다. 최종 전송 문자의 0/1 극성·정확한 설치 스케치는 여전히 미확인입니다. [최종 역할 설명](FINAL_ROLE_DIVISION.md).

## 직렬 제어 프로토콜은 단일 버전으로 확정되지 않음

- 01·04~07은 Arduino 측이 **숫자를 받는 형태**이며, `receivedNumber != 0`이면 정지하는 버전도 있습니다.
- 03은 **Pi가 보내는 `0`은 정지, `1`은 라인 추종**하려는 코드이나, `Serial.read()` 처리 오류가 보입니다.
- 이전 개발 대화의 `r:g:b:button` 요청 → Pi `result=0/1` 회신과는 **메시지 포맷 및 신호 의미가 일치하지 않습니다**.
- `Serial.print("Received number: ")` 같은 디버깅 문자열이 통신 포트에 함께 나가면 파이썬 수신 파서가 의도하지 않은 문장을 받을 수 있습니다.

따라서 **한 버전을 다른 버전의 실제 연동 상대라고 단정해서는 안 됩니다**. 당시 Arduino/Python 쌍과 시리얼 로그가 함께 남아 있다면 비로소 정확한 최종 통신 계약을 확인할 수 있습니다.

## 기존 복원본에 반영할 수 있는 사실과 금지사항

**반영 가능:** IR 핀 7/8과 9600bps 및 모터 핀 5/6/9/10이라는 구체적인 사용자 제공 코드 근거, 300ms 주기 시험, 버튼 재출발 상태, 실험적인 RGB `map(raw,0,21504,0,1025)` 스케일링, 사람 수와 색상 조건의 조합을 시도한 사실.

**임의 반영 금지:** 실제 2023년 최종 실행 버전 단정, 300ms 고정 응답 보장, 모든 버전의 0/1 의미 통일, 스케치 06의 `>=100` 분기 수정 내용을 역사적 코드라고 표시, 마이크로컨트롤러에서 의도한 물리 정지가 실제 구현됐다는 주장.

현재 루트 `arduino/line_tracer/line_tracer.ino`와 `raspberry_pi/main.py`는 여전히 **2026년 대화 기반 통합 복원**입니다. **실제 사용 스케치라는 인증을 추가하지 않습니다.**

## 시리얼 시험 사진

추가 제공된 Raspberry Pi VNC 및 Geany 터미널 사진에는 `Received from Arduino` 등 시리얼 송수신 시험으로 해석할 수 있는 로그가 보입니다. **시리얼 문자가 교환된 시험 증거**이지 실제 차량형 라인트레이서의 최종 주행·사람 감지 정지 통합 성공은 증명하지 않습니다. 연결 대상이나 정확한 시험 소스 버전도 사진만으로 확정되지 않습니다.

해당 화면에는 IP주소, 데스크톱 화면 및 기타 정보가 포함되므로 개인정보·접속정보 확인 전 사진 원본을 저장소에 게시하지 않습니다.

## 실제 성공과 버전 미확정의 구분 (사용자 2026-10-31 추가 회고)

사용자는 **실제 2023년 사람 인식 시 정지 시험에 성공**했다고 확인했습니다. 연산 지연으로 정지 구간을 지나치는 문제가 있어 인식 연산 간소화·감지 시점 선행 조치를 했으며, 물품 적재 후 버튼 입력 시 일정 시간 색상 기준 정지를 무시하도록 구현했습니다. 다만 이 개발 스케치 7개 중 **어느 것이 최종 성공 코드인지**는 여전히 미확인입니다. 이 사실은 [실제 시험 기록](2023_FIELD_TEST_AND_LATENCY_IMPROVEMENT.md)에 따로 정리했습니다.


## 7번째 스케치의 상세 검토 (ChatGPT 수정 제안, 실제 업로드 미확인)

- **수정된 지점:** 6번 스케치의 `lastCommunicationTime=currentTime` 직후 수행하던 불가능한 `>=100` 분기를 없애고, 300ms 주기 수신 검사 후 `moving && receivedNumber==0`일 때 `move()`를 호출합니다. 이 수정은 **소스 비교로 확인되는 사실**이지 실제 정지 응답 시간 개선을 입증하는 측정은 아닙니다.
- **다른 정지 부호:** 이 스케치는 `receivedNumber != 0`이면 정지합니다. Pi 쪽 대화 기반 `result=0` 정지·`1` 주행과 반대이므로, 최종 연결된 코드 쌍은 미확정입니다.
- **버튼 주행 위험:** `receivedNumber`가 정지 값으로 유지되더라도, 버튼을 누르면 `while (millis()-buttonPressTime<300) move();`로 **최대 약 300ms 동안 모터에 주행 명령**을 보낸 뒤 루프 끝에서 정지할 수 있습니다. 버튼을 계속 누르고 있으면 정지 후 다음 반복에서 같은 동작이 다시 발생할 수 있습니다. 코드 경로 분석이며 실제 기기에서 이런 위험 동작이 일어났다는 증거는 아닙니다.
- **응답 지연:** 300ms는 **통신을 확인하는 조건 간격**이지 정지까지의 보장된 최대 시간은 아닙니다. `Serial.parseInt()`의 대기 동작과 버튼 루프가 응답을 지연시킬 수 있습니다.
- **색상/카메라 미포함:** 이 스케치에는 TCS34725 색상 센서 판정, 사람 인식 연산, 적재 후 **색상 정지 구간의 1~3초 무시 처리**가 들어 있지 않습니다. 따라서 사용자가 직접 성공을 확인한 전체 적재 시나리오가 이 스케치 단독으로 입증되지는 않습니다.
- **구체 수치:** IRL=7, IRR=8, PWM=5/6/9/10, 버튼=3, 9600bps, speed=255는 제공 소스에서 확인됩니다. 실장된 최종 하드웨어 설정과 완전히 일치한다는 추가 증거는 없습니다.

**7번은 사용자 원문이 아니라 ChatGPT 제안 코드입니다. 원문을 수정해 컴파일·실행했다거나 7번이 최종 성공 스케치였다고 주장하지 않습니다.** 앞서 사용자가 확인한 실제 사람 인식 정지 성공과 지연 개선 경험은 [별도 회고 기록](2023_FIELD_TEST_AND_LATENCY_IMPROVEMENT.md)을 기준으로 유지합니다.
